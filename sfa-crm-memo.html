これまでの打ち合わせ・手書きメモ（清書版）をもとに整理　／　2026-11-05 時点
現時点の要点
  • 案件 ＝ 1つの目標に向けた一連のアプローチを束ねる単位。次回の接触予定があれば案件として登録する。
  • 営業活動は案件なしでも保存できる。次回商談が決まったら案件を作って紐付ける。
  • 次回予定（アラート対象）は案件だけに持たせる。
  • 環境は既存の「対応管理」と同じ構成。スマホ対応は必須。Java 21 / Spring Boot 3.x / PostgreSQL 16 / Thymeleaf + Bootstrap。

▶ 画面イメージを見る（6章）

1. 基本方針

  • 営業活動の記録は、案件と紐付けなくても保存できるようにする
  • まずは小さく作り、実際の営業で使えることを優先する（顧客・案件・活動・次回対応・一覧）
  • 外出先からスマホでその場で登録できること（戻ってから入力では使われなくなる）
  • 利用者ごとのアクセス権限とデータ保全を考慮する

2. 「案件」の定義

項目内容
定義1つの目標に向けた、複数回のアプローチを束ねる単位（例：「A社 DX推進」）
登録タイミング次回の接触予定（次回架電日・次回商談など）が決まった時点で、いったん案件として登録する
案件にしないもの初回で断られ、次回予定がないもの → 顧客に対する活動記録として残す
終了ステータスを受注／失注／保留にして閉じる（アラート対象から外れる）
この定義の理由「受注確度が上がったら案件化」だと、それ以前の商談履歴を案件にまとめて残せないため

3. データ構成（エンティティの関係）

  • ユーザー（自社の営業）・顧客・営業活動・案件は相互に関連する
  • 顧客には「担当者（顧客側）」が複数紐付く
  • 営業活動の案件IDは任意（NULL可）。案件がなくても顧客に対して記録できる
  • 次回対応予定日は案件だけに持たせ、アラートは案件だけを見る

4. アプローチと案件の紐付けパターン

パターン内容
アプローチ1顧客に対して記録する。案件には紐付けない（例：初回で断られた）
アプローチ2次回商談が決まった → 案件を作成して紐付ける（それ以前の活動もこの案件に紐付け直せるようにする）
アプローチ3既存の案件に活動を追加する

5. 画面遷移（案）

トップ（ダッシュボード）
 ├─ 案件の編集 ・ 営業活動の登録
 ├─ 営業活動の登録 ・ 案件の登録
 └─ 顧客の登録（トップから直接行けるようにするか要検討）

活動を記録する画面で、次回予定とステータスも一緒に更新できるようにし、入力の手間を減らす。

「読んだけど未対応」追うには「対応完了」フラグが必要（ないと通知欄に残り続ける）。ルームを開くには画面遷移を挟むので、既読フラグだけで十分という意見あり要検討
仮アポの扱い「前向きな反応はあったが日程は未確定」という状態をステータスとして管理する定義を確認
顧客側の担当者担当者A・B・Cを登録し、「誰につないでもらったか」「誰に引き継がれたか」を追えるようにする要ヒアリング
資料管理Zoho WorkDrive などのURLを顧客・案件に紐付ける有力

補足（提案）：既読の持ち方

既読を true/false で持つと、新着メッセージが来たときに未読へ戻す処理が必要になり、行数も増えやすい。中間テーブルには「最後に読んだメッセージID」を持たせると、未読判定・未読件数・「既読n人」の表示がまとめてできる。

room_members（ユーザー × ルーム）
  user_id               ユーザーID
  room_id               ルームID
  last_read_message_id  最後に読んだメッセージID
  → 未読 = そのルームで last_read_message_id より新しいメッセージがある

9. 確認事項（要ヒアリング）

  1. 「案件」の定義（2章）でよいか
  2. 顧客に対して営業担当は1人だけか
  3. 外部カレンダーとの連携は必要か
  4. 現状、資料をどのように管理しているか
  5. 活動内容の承認フローは必要か
  6. 「仮アポ」の定義
  7. 顧客側の担当者を登録できるようにすべきか
  8. チャット機能をこのシステムに作るか、Zoho Cliq を使い続けるか（Cliq なら既読管理は不要）
  9. 「読んだけど未対応」の通知を初期リリースに入れるか
  10. 「サバマル」「ETN」が何を指すか／「対応管理」のログイン（認証）の仕組みを流用できるか
  11. 利用人数と権限の分け方（他の人の案件を見てよいか）、既存データの移行の有無

10. 参考：将来の追加機能で比べる React と Thymeleaf＋JavaScript

現時点の方針は Thymeleaf＋Bootstrap＋JavaScript（8章）。この章は、今後機能が増えたときに React を選ぶとどんな利点があるかを整理した判断材料です。

10.1 前提：処理の流れの違い

観点Thymeleaf＋JavaScriptReact（＋Spring Boot API）
HTMLを作る場所サーバー（Java）が完成したHTMLを返すブラウザ（JavaScript）がJSONから画面を組み立てる
画面の更新基本はページ単位で再読み込み。部分更新は fetch で自前実装変わった部分だけ自動で書き換わる
画面の状態管理DOMを直接操作。画面が複雑になるほど「どこで何を書き換えたか」が追いにくい「データ（state）が変われば画面が変わる」仕組み。複雑な画面でも整理しやすい
部品の再利用Thymeleafのフラグメント（th:replace）で共通化。動きは別のJSに書く見た目と動きを1つのコンポーネントにまとめて使い回せる
ライブラリ素のJS（バニラJS）向けのものを組み合わせる。数は多いが、つなぎ込みは自前React専用の部品が非常に多い。組み合わせ方の情報も多い

10.2 追加機能ごとの比較

「差」：◎ React が大きく有利／○ React がやや有利／＝ ほぼ同じ（主にサーバー側の仕事）

追加機能Thymeleaf＋JSでの実現Reactでの実現Reactにするメリット差
カレンダー表示FullCalendar（素のJS版）を読み込み、予定をJSONで渡すFullCalendar（React版）、react-big-calendar など予定の追加・ドラッグ移動のあと、一覧やダッシュボードの数字も自動で更新される。カレンダーとフォームの連動が書きやすい○
案件カンバン（ステータスをドラッグで変更）SortableJS でドラッグ＋fetch で保存。列の件数などは自前で書き換えdnd-kit などドラッグ後に件数・金額・カードの表示がまとめて正しく更新される。失敗時に元へ戻す処理も書きやすい◎
チャット（リアルタイム）WebSocket（STOMP）で受信し、DOMにメッセージを追加する処理を自前で書く同じWebSocket＋チャットUI部品新着メッセージ・未読バッジ・入力中表示などを、別々の画面部品へ一貫して反映できる◎
通知・未読バッジの即時更新定期的に fetch して数字を書き換えるTanStack Query などで定期取得・自動更新ヘッダー・ダッシュボード・一覧など複数の場所のバッジが同じデータから自動で揃う○
@メンション入力Tribute.js などで候補を表示Tiptap、react-mentions など候補の絞り込み・選択・通知先の保持を部品にまとめやすい○
高機能な表（並べ替え・絞り込み・列固定・大量データ）DataTables、Tabulator などTanStack Table、AG Grid など絞り込み条件をURLや他の部品と連動させやすい。表の中で直接編集する機能も作りやすい○
ダッシュボードのグラフChart.jsRecharts、Chart.js（React版）などグラフをクリック → 下の一覧が絞り込まれる、といった連動が書きやすい○
日付・時刻の入力ブラウザ標準の date 入力、flatpickr などreact-day-picker、MUI の DatePicker など見た目を揃えた部品がそろっている。ただし標準入力でも実用上は十分＝
顧客名の候補表示（オートコンプリート）Tom Select などReact Select、shadcn/ui の Combobox など選んだ顧客に応じて案件の選択肢を切り替える、といった連動が簡単○
入力フォームのチェック・自動保存HTML標準のチェック＋サーバー側の検証。自動保存は自前React Hook Form＋Zod など入力中にその場でエラーを出す、下書きを自動保存する、入力に応じて項目を出し分けるのが楽○
ファイルのドラッグ＆ドロップDropzone.js などreact-dropzone などアップロードの進み具合・プレビュー・失敗時の再送を画面に出しやすい○
地図表示（顧客の所在地）Leafletreact-leaflet地図と顧客一覧の連動（地図で選ぶ → 一覧が絞られる）が書きやすい○
スケジュール・ガントチャートFrappe Gantt など専用ライブラリ多数選べる部品が多い○
モーダル・トースト・タブなどUI部品Bootstrap のJS部品shadcn/ui、MUI など見た目と動きをまとめた部品を使い回せる。デザインを揃えやすい○
オフライン入力（電波のない場所で入力し、あとで送信）Service Worker を自前で実装。難度は高いPWA構成＋状態管理のライブラリオフライン時の一時保存と再送の仕組みを組み込みやすい◎
スマホアプリ化Webのまま（ホーム画面への追加まで）React Native で、考え方や一部のロジックを流用できる将来ネイティブアプリにする場合の土台になる◎
外部カレンダー連携（Google／Outlook）サーバー側（Java）でAPI連携。画面の作りはほぼ関係ない差はほとんどない＝
CSV出力・取り込みサーバー側の処理が中心取り込み前のプレビュー・エラー表示はReactのほうが作りやすい＝
帳票・PDF出力サーバー側の処理が中心（Thymeleafのテンプレートを流用できる分、こちらがやや有利）なし＝
権限による表示の出し分けSpring Security＋Thymeleafの sec:authorize で簡単に書けるAPIで権限情報を受け取り、画面側でも制御する（サーバー側のチェックも必須）なし。Thymeleafのほうが簡単＝

10.3 まとめ：React のメリットとデメリット

メリットデメリット
  • カレンダー、カンバン、チャットなど動きの多い画面を作りやすい
  • 画面の一部だけが書き換わるので、操作がサクサクする
  • 部品（コンポーネント）として見た目と動きを使い回せる
  • ライブラリと情報（記事・サンプル）が非常に多い
  • オフライン対応・スマホアプリ化など、将来の拡張に強い
  • フロントとサーバーが分かれるので、APIを他のシステムからも使える
  • React を書ける人しか画面を直せない（属人化のリスク）
  • フロントとAPIの2つを作るので、工数が増える（目安：MVPで＋1〜1.5人月。要確認）
  • API用の認証（CSRF／CORS など）を別に設計する必要がある
  • Node.js・npm のビルド環境とライブラリの更新管理が増える
  • 既存の「対応管理」と構成が揃わない
  • 今の機能（登録・一覧・ダッシュボード）だけなら、Thymeleafでも十分に作れる

10.4 判断の目安

  • Thymeleafのままでよい：機能が登録・一覧・ダッシュボード・アラート中心で、保守をチームの誰でもできるようにしたい場合（＝現時点の方針）。
  • Reactを検討する：カンバン・リアルタイムチャット・オフライン入力・スマホアプリ化のうち複数を本気でやることになり、かつReactを書けるメンバーが2人以上いる場合。
  • 途中から切り替えることもできる：最初はThymeleafで作り、サーバー側の処理（Service層）を画面と分けておけば、あとからAPIを足して特定の画面だけReactにする、という段階的な移行が可能。
打ち合わせ内で表現が食い違っていた点：初期の打ち合わせでは「活動記録は案件に紐付ける」、手書きメモでは「案件なしでも保存できる」となっていたため、本メモでは後者（案件は任意）で統一しています。
